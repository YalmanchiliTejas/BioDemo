# Hybrid models, site adaptation and calibrated uncertainty

This page explains the neural hybrid, adaptation, uncertainty and transfer-decision layer
added on top of the [model library](LIBRARY.md). Work through
[notebook 03](03_hybrid_adaptation_and_uncertainty.ipynb) alongside it; it calls the same
backend code as the product API and assistant.

> All executable examples use **synthetic** data generated by the physical solvers from an
> authored "true" rate law. They show that the code behaves as specified. They are not
> evidence of real-world accuracy, calibrated coverage, customer validation or saved effort.

## What the physical models calculate

**`chemical.parallel_batch`** is a constant-volume batch with a desired pathway A → B and
an impurity pathway A → I, Arrhenius rates and a lumped energy balance:

```text
dN_A/dt = -(r_B + r_I)      dN_B/dt = r_B      dN_I/dt = r_I
r_j     = m_j · k_j(T) · N_A                        (mol/s)
ρ V c_p dT/dt = (-ΔH_B) r_B + (-ΔH_I) r_I - U A (T - T_c)
```

The unchanged physical model uses `m_B = m_I = 1`.

**`fermentation.oxygen_transfer`** is the existing algebraic scale-up relation for power
density and oxygen transfer (`kLa ∝ (P/V)^α · vvm^β`). It contains no growth, substrate or
product kinetics, so it cannot predict titre, yield or quality.

## What the neural component learns

| Adapter | Learned term | Unit | Allowed range | Network inputs |
|---|---|---|---|---|
| `chemical.parallel_batch` | `m_B`, `m_I` multiplying the Arrhenius rates | dimensionless | 0.25–4 | temperature (K), remaining reactant fraction, area/volume (1/m), U (W m⁻² K⁻¹), coolant temperature (K) |
| `fermentation.oxygen_transfer` | multiplier on predicted kLa | dimensionless | 0.25–4 | log P/V, log vvm, log working volume, impeller diameter (m), submerged impellers |

The rules:

- **The balances never change.** The network only scales a named rate inside the existing
  equations, so `N_A + N_B + N_I` is conserved whatever it outputs. The solver rejects any
  multiplier outside the bounds.
- **Inputs are physical states, operating conditions and characterised equipment features
  only.** Site names, run or batch IDs, time and future observations are never features.
- **The output is bounded.** A scaled sigmoid output keeps every multiplier inside 0.25–4.
- **There is no residual correction on the outputs.** A model that needs a new pathway gets
  a model-extension proposal (below), not a neural patch.

### Training procedure

The approach follows Al-Ramadhan et al., *Biotechnology and Bioengineering*,
[DOI 10.1002/bit.70385](https://doi.org/10.1002/bit.70385), as a two-stage method:

1. **Estimate bounded, regularised, state-dependent parameters.** For each interval between
   consecutive measurements of a training batch, the integrated species balances give an
   interval-effective multiplier. A bounded least-squares fit with a smoothness penalty and a
   pull towards 1 keeps them admissible.
2. **Learn their mapping.** A 6-unit tanh network maps the features to those multipliers.
   Each batch carries equal weight, regardless of how many time points it has.
3. **Embed the network in the solver.** Regularisation is chosen on the *selection* batches
   by comparing three candidates: unchanged physics, an ordinary constant-multiplier refit
   and the hybrid. The checkpoint records the selected model.

An ensemble of 2–8 members is built by bootstrapping **whole batches**.

### Departures from the paper

The checkpoint records these departures in `methodological_departures`:

- Rate estimation uses integrated species balances with *measured* temperatures, not the
  paper's full nonlinear time-varying-parameter trajectory optimisation.
- The fermentation adapter learns an algebraic kLa factor. The paper learns kinetic
  parameters of an organism model, which this repository does not have.
- The network is much smaller (6 hidden units) because development datasets are small.
- The source-weight penalty is a smooth approximation of L1. The paper selected a penalty
  of 0.01, and this code uses the same value.
- The code does not reproduce the paper's yeast or astaxanthin results. The paper's raw data
  are available only on request.

## How adaptation works

1. Train a **source** checkpoint on source-site batches.
2. Import receiver-site batches with their own train/selection roles.
3. Run `adapt_hybrid`. Training starts from the source weights and keeps the source input
   normalisation. It adds a penalty on the distance from the source weights
   (`source_penalty = 0.01`).
4. The adapted checkpoint is a **new, separate record**. It stores
   `source_checkpoint_hash`, so the source can be audited and is never overwritten.
5. **Negative transfer.** On receiver selection batches the adapted hybrid is compared with
   the source checkpoint, unchanged physics and the refit. If it is worse than the best of
   them by more than 1%, it is marked `negative_transfer` and `withheld_negative_transfer`.
   Simulation and interval operations then refuse to use it. This is a heuristic threshold,
   not a significance test.

A source checkpoint applied to receiver equipment outside its training feature range is
flagged `out_of_domain`. The result then abstains from calibrated intervals and risk
statements.

## How uncertainty is handled

The library keeps four kinds of uncertainty separate:

| Kind | Representation | Calibrated? |
|---|---|---|
| Measurement | declared `measurement_std` per observation, added after the conserved solve | no, only declared |
| Parameter | declared distributions on adapter inputs (with checked units), propagated through the solver | no, only declared |
| Learned model | spread across whole-batch bootstrap ensemble members, each run through the solver | no, ensemble spread only |
| Structural discrepancy and unsupported conditions | not quantified; out-of-domain inputs cause abstention | never |

Each source is also propagated on its own and reported as sample trajectories. These are
**not** additive variances.

An ensemble band is the 10th–90th sample quantile. It is labelled
`NOT calibrated intervals`, with `calibration_status: uncalibrated` and
`risk_probability: null`. Sensitivity sweeps are labelled the same way.

### The separate calibration layer

`calibrate_intervals` applies split-conformal calibration over **whole independent
batches**:

1. For each calibration batch, it computes the ensemble band and the score
   `s = max over the batch's grid of max(lower − y, y − upper, 0) / scale`.
   The score is the worst normalised miss, so the target is simultaneous coverage of the
   whole grid.
2. With `n` batches and miscoverage `α`, it takes `q = s_(⌈(n+1)(1−α)⌉)`.
3. Future bands widen by `q · scale`.

The status is `uncalibrated` (and `q` is `null`) unless all of the following hold:

- at least **9** calibration batches;
- every batch classified `measured`, `measured_unverified` or `published_experimental`,
  with a stated `independence_basis`;
- no failed or out-of-domain calibration predictions;
- batches disjoint from the training and selection batches and runs of the checkpoint;
- a common observable, unit, scale and prediction grid.

Synthetic batches are never eligible, however many IDs they carry.

**Assumptions behind any coverage statement:** calibration and future batches are
independent and exchangeable, from the same measurement basis and operating population.
Training, selection and augmentation are finished before calibration. Coverage is
*marginal over batches*, not a guarantee for one batch, and it says nothing about operating
conditions outside the calibration support. Such inputs make predictions abstain.

`evaluate_intervals` runs only on untouched `test` batches. It reports per-observable RMSE,
interval width, whole-batch coverage with its denominator, abstentions, failed predictions
and constraint violations.

### Data partitioning rules (enforced, not advisory)

- Every run belongs to exactly one of `train`, `selection`, `calibration` or `test`. A
  `(site, batch)` pair cannot appear in two roles, and shared source-run aliases cannot
  cross roles.
- Augmented runs must be `train` runs with an `origin_run_id` from the same site and batch.
- With `site_holdout`, a receiving site used for final evaluation cannot appear in
  development.
- Observations after a run's `evidence_cutoff` are rejected.
- Time points and replicate summaries are never counted as separate calibration batches.

## From predictions to transfer decisions

`assess_transfer` evaluates explicit criteria, each with a metric, unit, measurement basis,
operator and limit, for example:

```json
{"metric": "product_yield_fraction", "unit": "fraction",
 "basis": "desired_product_mol_per_initial_reactant_mol",
 "role": "yield", "operator": ">=", "limit": 0.2}
```

- Conversion is rejected as a yield metric.
- A criterion for an attribute the model does not predict, or on a different measurement
  basis, is **withheld**. The overall conclusion is then
  `withheld_missing_quality_evidence`.
- `noninferiority` needs an independently calibrated donor–receiver *difference* interval.
  A non-significant difference or a marginal band is never accepted. Without the difference
  interval the check is withheld.
- Every result is `draft_requires_engineering_review` and carries no risk probability.

`experiments` ranks up to 12 feasible candidate measurements for one identified decision.
The ranking favours candidates whose modelled spread straddles the decision threshold,
relative to measurement resolution and cost. Each entry includes the measurement,
conditions, rationale and limitations. This is a transparent heuristic, **not** expected
information gain. Out-of-domain, failed or uninformative candidates are rejected with a
reason.

## When the physics itself is wrong: model-extension proposals

Evidence sometimes points to a missing or changed mechanism, such as a consecutive
over-reaction or a new transport limitation. Use
`POST /v1/process-model/model-extension-proposals` (assistant tool
`model_library_propose_extension`) for these. The proposal records:

- the mechanism change, affected equations and conservation impact;
- the limiting case that must reproduce the current model;
- new parameters with units, bounds and the measurement that identifies each one;
- a verification plan and the evidence inspected.

It goes through the existing approval service as `review_model_extension` (engineering
role). It stores the current version and implementation digest and **does not change the
registered model**: `registry_status: unchanged`, `execution_permission: none`. Proposals
that only rename existing fit parameters are refused; those values are refitted with `fit`.
An approved proposal is a specification for a new versioned adapter. Checkpoints and
calibrations tied to the old digest must then be rebuilt.

## Evidence, permissions and invalidation

Configurations, datasets, plans, results, checkpoints and interval calibrations are all
derived records in the existing evidence store, with their inputs linked. Correcting a
source packet marks every dependent record stale. Stale library results withhold their
outputs. `refresh` rebuilds a configuration from the current source revision, and affected
work must then be prepared again explicitly. A standing assistant mission can do this
without a new user message. Site permissions apply through the whole lineage, and the
assistant never sees stored calibration or test observations when planning.

## Data required to calibrate a real customer process

These are the minimums for each step. They are not a guarantee of adequacy.

| Purpose | Data |
|---|---|
| Configuration | Versioned equipment characterisation (volume, heat-transfer area, measured U or its test, coolant conditions, impeller geometry), material properties and recipe set-points, each with source, unit and uncertainty |
| Fitting physical parameters | Time-resolved measurements of the model's observables (e.g. A, B, I by a validated assay and temperature) from several batches spanning the intended operating range |
| Training a hybrid term | Enough informative batches that the rate is excited across temperature and conversion; the code requires at least two training batches and four matched time points per batch, but useful learning needs considerably more |
| Model selection | Separate batches not used for training |
| Interval calibration | **At least 9**, preferably 20 or more, independent *measured* batches on the same assay, unit and time grid, with a documented independence basis and no overlap with development |
| Final evaluation | Further untouched batches, ideally including the receiving site's equipment |
| Receiver adaptation | Receiver-site batches with their own train and selection roles; characterised receiver equipment |
| Quality decisions | Direct measurements of each quality attribute in the acceptance criteria. The model cannot supply attributes it does not calculate |

Retain original files and hashes, units, assay method and version, sampling times,
exclusions with reasons, and the person accountable for each dataset.

The public oxygen-transfer dataset preserved in
`backend/src/lifesci/fermentation/data/oxygen_transfer_darus_5953.*` (DaRUS 10.18419/DARUS-5953,
CC BY 4.0) holds 24 configuration/condition **means** from one 30 L apparatus. It is not
24 independent batches. It is suitable for a narrow transport check, not for calibration
coverage or scale-up validation. See
[the research note](../research/pharmaceutical-hybrid-method-and-data-20261108.md).

## Known limitations

- **No real-data validation.** Every number produced so far comes from synthetic data. The
  hybrid outperforming the refit on synthetic data reflects how the data were generated.
- **Narrow hybrid scope.** Only two adapters support hybrid terms. The fermentation one is
  algebraic transport, not organism kinetics.
- **Negative-transfer rule.** It is a 1% threshold on selection RMSE, not a statistical
  test. With few selection batches it is noisy.
- **Experiment ranking** is a heuristic proxy, not expected information gain or a
  feasibility check.
- **Uncertainty sources.** Structural discrepancy is not quantified, and the four
  uncertainty components are not decomposed into additive variances.
- **Conformal coverage** is marginal, assumes exchangeability and does not extend beyond
  the calibration population.
- **Wall-time budget.** The budget is checked at admission and completion; it does not kill
  a running worker.
