# Proactive assistant references and existing Prime integration

Research date: 2026-11-02. Read-only source/code audit; no model runs, deployment checks, credentials, or implementation changes. The user confirmed [OpenAI Dots](https://chatgpt.com/features/dots/) by URL. Muse's identity remains provisional: the candidate audited here is Meta Muse. Other products use this name. The findings below concern these two first-party products only; the Muse findings are conditional on that identity.

## Job and governing direction

Help a person keep an ongoing manufacturing responsibility moving: understand a request, use authorized existing evidence, do useful background work, return a reviewable result or decision, and respond to corrections without restarting. This is broader than investigating a latest deviation. [Governing principles](../../Main_Culture_andETHOS.md), [glossary](../../GLOSSARY.md).

## What the reference products actually document

**Dots:** OpenAI documents work continuing between conversations, agent-selected pauses/wakeups, supported event triggers, recurring schedules, and background delegation. Conversation context, saved notes, and retrieved history are distinct; a child task does not automatically receive all conversation history. Proactive research is read-only and can inform suggestions; it cannot itself change connected apps or control a browser. Connecting a service alone does not establish a monitoring task. These are useful distinctions for Sievance's authorization and memory contracts. [Official OpenAI documentation: tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory).

**Muse experience:** Meta describes concurrent work alongside conversation, scheduled/event-driven follow-up, and a decision about whether a background result warrants interrupting the person. Goals, activity, editable memory, and structured approval controls are visible separately. Artifacts can take the shape required by the task rather than only conversational prose. These are documented product choices, not evidence that Sievance should copy a main-chat interface. [Meta's product design account](https://introducing.muse.ai/).

**Muse harness/security:** Meta explicitly describes a dedicated VM, an agent runtime container with a filesystem/terminal/browser, skills/connectors, and separate durable application state. Its Sentinel is the authority for connector actions and network egress; credential services sit outside the agent cell, with credential insertion at the authorized boundary. This is a published security design, not a reusable open-source harness specification or evidence that equivalent guarantees exist in BioDemo. [Meta's technical account](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse).

**Unknown:** These sources do not establish the complete proprietary planning algorithms, scheduling heuristics, memory ranking, notification thresholds, or deployment economics. Dots' product behavior is documented; its internal daemon/queue/database architecture is not established by this audit. Do not invent these internals or imply that a specific vendor design caused observed quality.

## Recommended extension, not a second agent loop

Reuse mission activation as the execution boundary and Prime as the bounded reasoning harness. Connect conversation intent, corrections, source events and timers to one owned mission. Assemble its authorized context, invoke the qualified Prime adapter when open-ended reasoning is warranted, and persist plan/progress/results through existing mission/evidence/action services. Keep deterministic work deterministic. The interface must pass explicit scope, evidence versions, event identity, budget and resume information, and must reject stale results before committing or proposing actions.

This needs a genuine general-purpose task contract in the existing harness, not production reuse of evaluation-only `task_answer`, and a permission-aware mapping from current platform evidence to the legacy manufacturing bridge. Neither a new parallel agent loop nor a handler hardcoded to the latest deviation supplies these contracts. Prime's legacy bridge scope string is not by itself proof of the current platform's tenant/role authorization. Preserve both boundaries while integrating them.

Compare two options: (1) explicit responsibilities plus bounded, event-triggered Prime work, with existing deterministic obligations retained; (2) broader standing proactive discovery with configurable relevance and notification policy. Start with the former to establish useful behavior and control inference/noise; adopt the latter only with measured benefit. Neither requires a second scheduler or copied VM architecture. [ADR 0003, currently proposed](../adr/0003-persistent-missions-and-runtime-boundaries.md) already separates missions from workers; [existing broader architecture proposal](../product/long-horizon-manufacturing-agents.md) explicitly recommends extending Prime. Earlier deviation-centric framing is historical, not product-wide direction.

Joint pillar checks: reduce manual setup by retrieving permitted context (Start); retain source versions, gaps and traceable interpretations (Trust); produce drafts, exact proposed actions and outcomes with existing human authorization (Act); reuse systems of record, runtime ports and existing tools (Adopt). Trade-off: standing discovery may find more opportunities but increases spend, privacy exposure and interruption burden.

Evaluate on varied requests and new evidence, correction during work, restart, duplicate wakeup, revoked access, stale output, budget exhaustion and unavailable provider. Measure user preparation and review time, evidence support, useful result/decision completion, missed/duplicate notifications, restart continuity and cost per useful outcome. Record outcomes before claiming improvement. No manufacturing validity, regulatory compliance, or measured time savings is established here.
