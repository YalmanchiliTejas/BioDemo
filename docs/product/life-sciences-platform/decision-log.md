# Decision log

Date: 2026-10-23. These are the engineering choices for the proposed implementation. They are documented now so a reader can understand alternatives and revisit them. They are not claims that corresponding code exists or that a customer has authorized a live deployment. Implementation/release evidence belongs in the [checklist](capability-checklist.md).

## Product and architecture choices

| ID | Decision and reason | Alternatives and trade-off | Revisit when |
| --- | --- | --- | --- |
| D01 | Cover the complete researched life-sciences capability set in one traceable plan. Preserve the user's broad product scope and long-horizon missions. | A deviation-only roadmap would omit lab, execution, network and platform work; doing all modules simultaneously would obscure integration risk. | User changes capability scope or source evidence adds a substantive offering. |
| D02 | Existing systems retain assigned official records; native execution is explicitly enabled per capability/site. | Replacing MES/LIMS everywhere simplifies local ownership but imposes migration and qualification burden. Integration adds reconciliation work. | A customer explicitly adopts BioDemo as authoritative for a defined workflow. |
| D03 | Begin with modular FastAPI domain services and separately scalable workers. | Immediate microservices add distributed transactions/operations; a single process cannot isolate expensive workloads well. | Measured bottlenecks or independent deployment/security boundaries require extraction. |
| D04 | PostgreSQL is the transactional domain authority; object storage preserves originals; analytics/search are projections. | Polyglot authoritative stores increase synchronization complexity; storing raw traces in transactional rows harms query cost. | Measured workload cannot meet targets after query/index/partition/worker improvements. |
| D05 | Use versioned current state plus append-only audit/events, rather than event-sourcing every domain object. | Universal event sourcing offers replay but greatly expands event evolution/reconstruction obligations. | A specific domain needs historical reconstruction beyond retained revisions/audit. |
| D06 | Commit domain changes and outbox intents transactionally; consumers deduplicate and external actions reconcile. | Synchronous multi-system writes couple availability; exactly-once assertions cannot cover arbitrary remote side effects. | Destination contracts or measured fan-out justify a new transport. |
| D07 | A persistent mission spans sessions and linked cases; it owns goals/unfinished work. | Incident-only sessions miss proactive batch/campaign work; one eternal process is fragile. | Real workloads show a different ownership/lifecycle boundary. |
| D08 | Keep Prime behind a versioned task/context interface as initial reasoning runtime. | Replacing it now discards integrated evidence and checks; keeping it requires mission/checkpoint improvements. | It fails continuity, isolation, tool or cost requirements that another harness demonstrably satisfies. |
| D09 | Select Temporal for production mission orchestration, timers and waits; keep domain records outside its history. | Existing jobs remain useful for bounded activities, but implementing multi-day timers/recovery/versioning ourselves adds maintenance. Temporal adds an operational dependency. | Deployment constraints prohibit it, or a simpler scheduler meets the full semantics with lower measured total effort. |
| D10 | Reconstruct bounded context from durable history, current state and evidence changes; keep originals recoverable. | Full-history prompts increase cost and noise; summary-only memory can lose critical details. | Measured context strategies improve retention/quality/cost for approved models. |
| D11 | Track dependencies from evidence to findings, fields, recommendations and approvals; invalidate on material changes. | Re-running everything is costly; retaining stale conclusions breaks trust. Dependency tracking costs metadata and engineering. | Invalidation misses important relationships or excessive fan-out demands better granularity. |
| D12 | Use role-specific skills/scopes; spawn bounded workers for independent work. | Separate permanent agents for every role add duplicated context, disagreement and cost. | Parallel specialists improve quality or completion time on representative tasks. |
| D13 | Use deterministic code for reliable rules/calculations, then evaluated small/balanced/frontier routing. | Frontier-everywhere wastes resources; small-everywhere can increase consequential omissions and retries. | Task evaluations or provider changes alter the cost/quality frontier. |
| D14 | Routing, authority and budgets are enforced outside the model; no silent quality downgrade on exhaustion. | Model self-reported confidence is cheaper to implement but not a calibrated risk or authorization mechanism. | New calibrated evidence supports limited additional automation. |
| D15 | Cost includes all descendants, retries, tools, review and infrastructure; optimize successful outcomes. | Token price alone hides failed work and reviewer burden. Full attribution requires shared run IDs and metering. | Accounting cannot attribute material spend or changes in workload require revised allocation. |
| D16 | Store procedure interpretations with provenance; require controlled publication for native executable procedures. | Blind document-to-code execution risks ambiguous instructions; mandatory hand-mapping burdens every user. | A qualified customer procedure family supports more automatic interpretation. |
| D17 | Approval binds to a specific proposal/record version; required new approval follows material changes. | Generic blanket approval is easy but ambiguous. Version-bound approval requires correction/expiry semantics. | Organizational policy defines different explicitly authorized scopes. |
| D18 | Preserve explicit prior-case reuse approval and distinguish prior proposals, execution and observed effectiveness. | Automatic similarity shortcuts may repeat a failed or inapplicable investigation. Approval adds targeted owner effort. | User and organization authorize a different policy backed by evidence. |
| D19 | Scientific claims use reproducible tools and qualified interpretation; optimization respects process/quality constraints. | LLM-only numeric/causal answers are flexible but difficult to verify. Method modules require domain validation work. | Appropriate evaluated models or experimental evidence justify additional capabilities. |
| D20 | Site collectors buffer and reconcile; high-rate telemetry becomes bounded analytical windows/change events. | Central model processing for every reading is costly and vulnerable to outages. Edge deployment adds lifecycle/security work. | Actual signal rates, connectivity or control requirements change. |
| D21 | Relational dependency edges and scoped text search first; add vector/reranking where retrieval tests justify it. | Dedicated vector/graph stores can help scale but introduce synchronization and authorization surfaces. | Retrieval accuracy/query load measurably warrants expansion. |
| D22 | Reuse AWS-compatible cloud-job/object foundations and container workers; preserve deployment adapters. | A new Kubernetes estate or serverless rewrite adds operations before demonstrated need. Some customer private deployments require alternatives. | Contracted deployment/residency/capacity constraints demand another topology. |
| D23 | Enterprise identity, non-owner database roles, explicit RLS and per-tool authorization protect shared state. | Application filters alone are easier but a missed predicate can leak data. RLS needs careful role/pool setup and tests. | Dedicated tenant installations or new grant models change isolation requirements. |
| D24 | Partner sharing uses explicit resource grants and scoped projections; one owning writer per aggregate/region. | Global unrestricted shared memory is easy but violates boundaries; multi-region writes create conflict complexity. | Contracted cross-region latency/availability requires a designed conflict model. |
| D25 | Integrate established media/collaboration transports; build domain-linked session controls and annotations. | Building video transport/AR infrastructure from scratch distracts from manufacturing value. Integration creates vendor/device dependencies. | Device/latency/data constraints make existing transports unsuitable. |
| D26 | Source claims, code presence, completed integration and verified behavior have separate checklist statuses. | One 'done' checkbox is simple but falsely conflates documentation with a working qualified system. | No relaxation; adjust the tracking format if it becomes difficult to maintain. |
| D27 | Define workload/SLO hypotheses and quality gates, then test; do not promise vendor deployment claims or fabricated accuracy. | Fixed marketing targets create apparent certainty without evidence. Measured targets need workload and customer input. | First baseline measurements and intended-use review establish defensible targets. |
| D28 | Deliver whole cross-domain scenarios in stages while retaining the complete capability inventory. | Building isolated modules independently leaves integration until late; a perpetual one-feature demo never addresses full scope. | Dependency or customer-value evidence changes phase ordering. |

## Implementation decisions (2026-10-23, build of `backend/src/lifesci/`)

These record choices made while implementing D01–D28. Each names what was built, what it trades, and when to revisit. Evidence lives in the [implementation guide](implementation.md) and the checklist's evidence columns.

| ID | Decision and reason | Alternatives and trade-off | Revisit when |
| --- | --- | --- | --- |
| D29 | New `backend/src/lifesci/` domain package instead of extending `benchmark/` or `cloud_backend/`. The benchmark package is explicitly not a production authority; the cloud backend is a job control plane. Existing connectors, Prime harness and OIDC verifier are reused by import. | Extending `benchmark/application` is faster but entangles demo fixtures with authoritative records; a separate repo/service adds deployment overhead before it is needed. | Modules need independent deployment (D03). |
| D30 | One generic versioned record store: `aggregates` (current) + `aggregate_revisions` + `audit` + `outbox` + `inbox` + `leases` + `edges` + `idx` + `blobs`. State is JSON per aggregate kind. Implements D04–D06 with one code path. | Per-domain normalized tables give stronger DB-level constraints and simpler ad-hoc SQL, but multiply migrations for each module. JSON state keeps domain evolution cheap; domain invariants are enforced in services and tests. | A kind needs relational constraints or analytical queries the JSON shape makes costly; then promote it to its own table behind the same service. |
| D31 | SQLite for local/tests, PostgreSQL in production through the same SQL. PostgreSQL path is migrated by an owner (`migrate_postgres`) and run as a non-owner role with `FORCE ROW LEVEL SECURITY` on every tenant table; audit and revision tables have append-only triggers. Verified against a throwaway local PostgreSQL 16 cluster. | App-level predicates alone are simpler but one missed predicate leaks data (D23). Separate per-tenant databases isolate better but cost more to operate. | Dedicated tenant installations are contracted. |
| D32 | A write transaction binds to exactly one tenant on first use; touching a second tenant raises `CrossTenantError`. On PostgreSQL the binding sets `app.tenant_id` for the transaction so RLS applies. | Allowing multi-tenant transactions would ease system jobs but weakens isolation; cross-tenant system work (outbox draining) runs per tenant or under a separate dispatcher role. | A legitimate cross-tenant transaction is required. |
| D33 | Secondary indexes are declared per kind (`DEFAULT_INDEXES`) and maintained in the same transaction as the write. Added after the load smoke showed partner grant checks at p50 35 ms with 2,000 grants (full scan); after indexing p50 3.6 ms on the same laptop/SQLite run. | A JSONB GIN index works only on PostgreSQL; per-kind tables (D30 alternative) cost more migrations. | New hot lookups appear in traces; add the field to the index map. |
| D34 | Signatures and approvals bind `(record kind, id, revision, content_hash)`. A changed record keeps the historical binding intact but the signature no longer covers current content. High/critical approvals require a re-authentication method reference. | Signing only the id is simpler but cannot detect content drift. Actual re-authentication is delegated to the identity provider; we record the method, we do not implement MFA. | The customer's IdP exposes step-up assertions we can verify cryptographically. |
| D35 | Invalidation rules are per kind: derived artifacts become `stale`; a queued intent becomes `awaiting_reassessment`; an already-sent intent or delivered proposal keeps its real delivery status and gains `needs_reassessment`; approvals, signatures, outcomes and evidence are never overwritten. | Uniform "mark stale" was the first implementation and would have erased the fact that an operation had been transmitted — caught during review before tests. | New record kinds with "already happened" semantics are added; register them in `_IMMUTABLE_KINDS`. |
| D36 | Model routing order: C0 deterministic handler → cheapest *evaluated* profile at or above the task's floor tier → escalation chain of other qualified profiles. A route only exists after a passing, threshold-checked `Qualification` with impact scope. Unknown task kinds raise (or, with the development flag, go to the frontier tier flagged `unqualified` and requiring review). | Routing by model-reported confidence is cheaper to build but uncalibrated (D14). Defaulting unknown work to the cheapest model saves money and risks silent omissions. | Calibrated evidence supports another policy. |
| D37 | Default registry lists Anthropic (Haiku/Sonnet/Opus 5.5) and OpenAI (Luna/Sol/Astra) candidates per tier with dated prices, none qualified by default. Providers are thin `httpx` adapters (no SDK dependency); stable system prompts are marked cacheable on Anthropic. | Vendor SDKs add features (streaming, retries) but add dependencies and divergent error types. | Streaming or tool-use loops are needed inside the gateway (Prime handles those today). |
| D38 | Gateway call policy: ≤2 retries for retryable provider errors; then a circuit breaker marks the profile unavailable for a cooldown (60 s default) and fails over to the next qualified profile; one targeted repair on validation failure; then one escalation; otherwise `unresolved`. Output validation: JSON object, schema fields/types, cited sources ⊆ supplied inputs, no `confidence_probability`. Results are withheld (`stale_basis`) if any input changed during the call. | Unlimited retries or silent fallback to unqualified models hide failures. | Measured repair/escalation probabilities justify different bounds. |
| D39 | Budgets are hierarchical (tenant → mission → root run) and reserved atomically for the worst case (estimated input + max output) before each call, then settled to measured usage. Exhaustion returns `budget_exhausted`; missions pause with `remaining_work`. Reviewer minutes are attached to runs so task cost includes review effort (D15). | Post-hoc accounting is simpler but cannot stop overspend. Worst-case reservation can block a call that would have fit. | Reservation causes measurable false blocks. |
| D40 | Missions: single coordinator via lease + monotonic fencing token; checkpoints stored as immutable content-addressed blobs and promoted by a revision-checked, fenced commit; wakeups coalesced with event ids preserved; context assembly never truncates objective, constraints, corrections, rejected hypotheses, open obligations, pending decisions or remaining work; compaction archives findings to recoverable blobs. The scheduler is a port (`MissionScheduler`); `InProcessScheduler` is implemented. **Temporal (D09) is not yet wired**: no Temporal server/SDK is installed in this environment, so the production durable-timer path remains unimplemented and is tracked as a gap. | Building on the in-process scheduler in production would lose timers on restart. | A Temporal deployment target is available; implement `TemporalScheduler` behind the port and run the V03/V12 scenarios. |
| D41 | Tenant-fair work queue: separate urgent lane always served first and exempt from the analysis concurrency ceiling; deficit round-robin across tenants for normal/background lanes; per-tenant queued and running ceilings; per-mission fan-out limit; explicit `Backpressure` instead of dropping; persisted items recovered after restart. In-memory index per process. | A broker (SQS/Kafka) gives multi-process distribution but adds infrastructure (D22). | More than one dispatcher process is needed; move selection into PostgreSQL `FOR UPDATE SKIP LOCKED` (as `cloud_backend` already does) or a broker. |
| D42 | API roles always come from stored, revocable assignments; the development resolver reads only tenant/actor headers, and production reuses `cloud_backend.auth.Verifier`. The existing demo app's practice of trusting role headers is not carried over. | Header roles are convenient for demos but let any client self-elevate. | — |
| D43 | Prime stays the open-ended investigation harness, but `PrimeInvestigationAdapter` now takes its model from the router and records cost into the same budget/trace ledger. Cost coverage is labelled `prime_root_session_only` because Prime child-session usage is still incomplete (known gap). | Re-implementing investigations inside the gateway would discard tested evidence tooling. | Prime exposes complete descendant usage. |
| D44 | Development delegation for this build followed D13: four bounded module implementations went to `claude-sonnet-5-5` (balanced), the assessment documentation to `claude-haiku-5-5` (small), and core contracts, gateway, missions, integration review and verification stayed with the lead model. Each delegated module was given the tested core API and reviewed/re-run by the lead. | Single-model development is simpler to coordinate but uses the most expensive model for routine work. Delegation risks modules diverging from the core; mitigated by one written contract (core API, rules, acceptance-named tests) and lead re-verification. | — |

### Follow-up decisions (2026-10-23, after user confirmed Temporal and UI wiring)

| ID | Decision and reason | Alternatives and trade-off | Revisit when |
| --- | --- | --- | --- |
| D45 | **Temporal adopted** (user confirmed D09). `TemporalScheduler` implements the existing `MissionScheduler` port; one workflow per mission (`lifesci-mission:<tenant>:<mission>`), signal-with-start for wake-ups, durable timers for the next unsurfaced obligation, continue-as-new after N activations, activities on a bounded thread pool with a 30 s heartbeat timeout. Mission records stay in the record store; workflow history carries only ids, reasons and times. Supersedes the "not yet wired" gap in D40. | A store-backed scheduler (polling due times with `SKIP LOCKED`) needs no new infrastructure but would re-implement timers, retries, history and versioning. Temporal adds a server to operate (cluster or Temporal Cloud) and workflow-determinism discipline. | Deployment cannot host Temporal; fall back behind the same port. |
| D46 | Activities judge "due" against the **workflow's time** (`as_of`), and an obligation records which due time was surfaced (`surfaced_due_at`). Found when the time-skipping test spun: a timer fired in workflow time while the activity compared against the worker's wall clock, so nothing was ever "due" and the workflow re-armed immediately. The same defect would appear in production as clock skew between workers and the server. A one-minute floor additionally prevents any already-fired due time from spinning. | Using wall-clock in activities is simpler but makes decisions depend on which machine runs them. | — |
| D47 | Activations run as the owner's **delegated agent** and release their lease at the end. A person with no current roles delegates nothing (fixed: an empty site list previously made a revoked owner's agent tenant-wide). A revoked owner therefore stops mission activations, which Temporal retries with backoff until authority is restored or the mission is cancelled. | Running activations as a privileged service identity avoids retry noise but would act beyond any person's current authority. | — |
| D48 | If Temporal is unreachable, wake-ups are written to an `orchestration_backlog` record and replayed (`replay_backlog`); mission state itself is already durable. In-flight upgrades are gated by `verify_replay(histories)` (Temporal `Replayer`) against recorded histories. | Failing the API request when the orchestrator is down would block user corrections and decisions on an infrastructure outage. | A backlog replayer daemon is needed (currently invoked by operations). |
| D49 | Tests replacing a worker disable sticky execution (`max_cached_workflows=0`) because the SDK's time-skipping test server does not hand sticky tasks back after a worker stops; verified separately that a real local Temporal dev server recovers with sticky execution enabled (replacement worker resumed in < 4 s). Production keeps Temporal's default sticky execution. | — | — |
| D50 | The React workspace gets an explicit **connected mode** alongside the unchanged browser-local sample mode: missions appear as work, proposals with server-side status, approvals only for roles the server reports as able to decide, and the context strip states the auth mode. New read endpoints (`/v1/me`, `/v1/missions`, mission notes, mission proposals with `can_decide`, outcomes, revisions) support it. The demo identity is never sent as roles. | Replacing local mode outright would break the documented sample walkthrough and its checks; keeping only local mode leaves the product disconnected from real records. | Sample mode can be retired once a hosted demo tenant exists. |
